# M3 runtime moderation and appeals

**DEFAULT (Oct 13 2026), owner can change.** `MODERATION_RUNTIME_ENABLED=false` by default. No staging, external DID verification, real moderation operator provisioning, or production approval.

When enabled, a locally active impersonation hold hides held subjects from `GET /api/profiles/{handle}` (404), failing closed on DB errors (503). Admin-only bearer-token APIs evaluate reserved/lookalike/distinct-reporter signals and open review cases, queue appeals, list bounded pending/historical cases, and decide upheld/rejected/released with a transactionally recorded admin audit event. A release deactivates the hold; reevaluation can reapply it if the underlying handle or reports still trigger screening. Pending case uniqueness prevents duplicate queue spam. Appeals currently are **admin-intake only**; no public appeal form or user self-service is exposed. Do not present local hold or local claim as independent PDS verification.

Paths: `POST /api/admin/moderation/subjects/{did}/evaluate`, `POST /api/admin/moderation/subjects/{did}/appeal`, `GET /api/admin/moderation/cases`, `POST /api/admin/moderation/cases/{id}/decision`. Sensitive POSTs use existing origin, Fetch Metadata and local rate limiting; all handlers require the configured admin bearer token. The operator identity in the audit is 'admin' because existing admin tokens do not identify an individual. **Owner action remains:** role-based named operator credentials, appeals intake with independently authenticated appellant, notification, abuse-of-report review, PDS-backed verification, cross-instance rate limiting, documented retention and false-positive appeals SLA. Current enforcement targets public profile lookup only; follow, claim, publishing and other future routes need their own authorization guards before this is production-ready.
