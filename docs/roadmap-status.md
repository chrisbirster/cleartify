## Key boundaries and sign-off

- **M0 is done:** the five decisions in #6 and retention engineering defaults were owner-signed. This is **not counsel approval** and **not permission** to publish those defaults as policy.
- **M1:** database-backed signup windows and consent version **keys** from #57 are internal plumbing; placeholder identifiers contain no approved legal language. Public privacy, terms and retention/deletion promises still require **counsel and owner review**. No counsel sign-off is asserted.
- **M2:** local or fake DID checks and authenticated code paths do not prove interoperability with a real PDS. Real-PDS verification and staging require owner resources and evidence.
- **M3/M6:** #58 provides process-local metrics and enforces impersonation holds on selected social block/report mutations only, **not** every social, creator, install, commerce or private route. Admin cases/appeals do not amount to a complete moderation operation.
- **M4:** #52 adds flagged publishing with provenance/visibility audit; it does not establish rights clearance, licensed third-party content, moderation/takedown completeness or owner-approved seeded catalog.
- **M5:** #53 persists authenticated *fake* run reservations/results/audit. The current fake executor does not authorize real code execution or establish production scheduling/recovery.
- **M7:** #54 uses a **fake** ownership verifier and no-I/O local test adapter. This is not private-key possession proof and does not establish a deployed self-hosted agent.
- **M8:** #55 authenticates signed in-process envelopes against stored keys and checks consent/grants transactionally, but stores pending messages without remote delivery; no outside-network agent-to-agent transport exists.
- **M9:** #56 is fake-provider-only and buyer-session-bound. Its entitlement check protects the **new access-check endpoint**, not all pre-existing paid content paths. No real provider, SDK, keys, money movement, chargebacks or seller launch terms.
- **M10:** #59 stages an in-memory database, in-process HTTP checks, fake payments and failure alert events. Its alert sinks are no-op or in-memory only; it is **not** a deployed, production-equivalent end-to-end test or external notification system.

## Owner-controlled remaining actions (not completed)

1. **Real-PDS verification and staging:** supply approved test accounts/environment, validate OAuth, linking, session expiry/revocation, handle changes and restarted flows, then complete staging smoke and security checks.
2. **Deploy and operational readiness:** authorize staging/production configuration, backup restore exercise, monitoring/alert recipients and operational ownership; no deploy is claimed.
3. **Real payment provider and seller terms:** select and approve a real provider and agreements, credentials, tax/payout/refund/KYC policies, seller terms and paid pilot; fake receipts are never real payment evidence.
4. **Legal:** owner and **counsel must review and finalize** /privacy, /terms, retention/deletion wording, copyright/license/attribution and commerce language. **No counsel sign-off has occurred or is claimed here.**
5. **Launch:** owner explicitly evaluates evidence, approves a release SHA and makes a **go/no-go** decision. Nothing in a green CI run implies launch approval.
